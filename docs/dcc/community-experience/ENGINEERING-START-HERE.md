## Read this first — operating contract
Always verify current GitHub branch HEAD, standard AND security CI, Vercel deployment SHA, Supabase applied migration versions, and target provider isolation before merging or changing runtime flags. No model may infer green CI from a prior SHA. No production migration, live account activation, Airtable contact mutation, unapproved member publication, mass email or infrastructure charge without scoped authorization. Use synthetic identities for preview QA. The purpose is a prospect-safe shared Atlas, then a verified, owner-editable Passport, then consent-based publication.

## Founder decisions, locked
1. ONE successful verified DCC website enrollment creates or reuses ONE private member identity/person node. Join, sign up, sign in, profile, and Passport are entry points to that same lifecycle. Repeat login/edit creates no duplicate. Canonical person data remains in the existing DCC CRM People base, while Supabase holds protected technical binding, event, draft and publication state; no second independently editable human directory.
2. Q1=A: verified website presence may eventually appear only in delayed and coarsened anonymous count snapshots. Neither the website identity nor private interests become publicly addressable. Named artist profiles and practice edges require separate explicit consent and human approval. Historical 101 WhatsApp-reported seats, website members and 72 poll category selections are separate cohorts with unknown overlap.
3. Q2: after a deliberate audited cutover, newly created Clerk platform accounts, including Smart Sign, enter the DCC private enrollment lifecycle. Pre-cutover users are not automatically backfilled by login. Email, WhatsApp display name and legacy CRM row are not authentication or ownership evidence.
4. Passport is the SAME person's durable private editor. A verified person can edit their private draft, including while reconciliation is pending. Public listing requires active verified binding, versioned opt-in, revision-safe human approval and a separate visibility switch. Revocation must remove published discovery without deleting private membership.
5. Mobile-first V1: Explore Atlas -> Join DCC / verified signup -> Your DCC -> private Passport (display name, summary, optional practices/interests/links, save and resume) -> optional listing request -> approved public Atlas/artwork. No mandatory detailed questionnaire, separate Passport account or competing browser-only profile wizard.

## Actual code path, and why it is not yet a live journey
The existing /join route defaults to the correctly labeled legacy CRM contact form while membership flags are OFF. Once deliberate gates are enabled it directs new users to Clerk signup and /network/your-dcc. The branded /sign-up and /sign-in preserve safe local redirects for legacy Smart Sign and DCC.
The signed Clerk webhook and reconciliation worker stage new verified identities, with collision and uncertain-provider holds. /api/dcc/membership/status serves private state. /network/your-profile and GET/PATCH /api/dcc/me supply protected owner draft, validated inputs and revision CAS. /api/dcc/me/publish is ONLY a publication request; steward revision/consent checks and a separate approved snapshot precede /api/dcc/sculpture/public discovery. /api/dcc/me/visibility withdraws published visibility without deleting membership.
Default-OFF controls include DCC_MEMBER_EVENT_CAPTURE_ENABLED, DCC_MEMBER_RECONCILIATION_ENABLED, DCC_MEMBER_PROFILE_ENABLED, DCC_STEWARD_IDENTITY_RESOLUTION_ENABLED, DCC_PUBLIC_ATLAS_MEMBER_VISIBILITY_ENABLED and DCC_SCULPTURE_SNAPSHOTS_ENABLED. Never turn these on in production to get tests passing.
The Atlas displays editorially curated preview profiles or an allowlisted published feed; there is no permission to expose raw People, private drafts, WhatsApp roster or individual poll ballots.
