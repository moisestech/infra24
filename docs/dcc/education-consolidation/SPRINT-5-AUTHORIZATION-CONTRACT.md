## Shared authorization interface (design only)
One server-only access service, not new authentication or workshop engine. Suggested signatures:
- resolveActor(): verified Clerk instance/subject -> existing approved Passport binding and active org memberships; anonymous distinct from unresolved auth; no caller-supplied IDs trusted.
- resolveOffering({orgKey,offeringKey}): validate/normalize known slug or UUID, return exactly one stored offering plus active owner tenant and approved content binding; ambiguity denies.
- authorizeEducation({action,actor,offering,chapter?,registration?,grant?,session?,environment}): returns allow with scoped projection intent or deny with internal reason; default deny. Load trusted relationships server-side; never use user-editable metadata as authorization.
- projectPublicOffering(row,approval): explicit DTO with nested reviewed fields, no private content or metadata spread. list and detail must enforce same policy before serialization; no staff-only fields in public cache. Public marketing approval is distinct from lesson version and rights approval.
- resolveApprovedChapter(offering,chapterKey): approved canonical content version + chapter ID, parent match, rights approval, reviewed safe Markdown and assets; no draft access through aliases. Staff metadata review is not rights clearance or runtime draft publication.
- authorizeOwnProgress(actor,offering,chapter,registration): active tenant/entitlement and own record, canonical chapter-parent/version; validate percent/time/completion and explicit unique conflict strategy. Staff analytics is separate from personal progress; no arbitrary impersonation.
- authorizeDeliveryGrant: verified grant issuer and target, version, scope, expiry and revocation. A public lesson may be read without grant, but institutional delivery is separate permission. No implicit partner edit or learner access.
- authorizeFacilitator / authorizeMailWorker: separately scoped operations; join code is not staff authority. Test mail isolated sink only; scheduled real mail out of pilot scope.
All allow decisions require explicit action-specific validation, safe projection, transactional integrity where needed, and runtime tests. Mixed routes must be split into distinct public/member/staff modes or separate handlers with caller migration; the JSON route mapping is minimum proposed action classification, not final handler wiring. Disabled legacy endpoints require compatibility review before retirement. Do not silently remove working institutional flows. No new production database grants or application code.
