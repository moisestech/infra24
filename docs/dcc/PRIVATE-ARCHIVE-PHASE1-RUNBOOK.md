# DCC private archive and commercial integrity — Phase 1
Status: synthetic rehearsal only; not a release candidate or hosted migration.

## Reproduce
Run from repository root using Python 3.10+:
```sh
python3 scripts/dcc/private-archive-rehearsal.py
python3 scripts/dcc/commercial-integrity-rehearsal.py
```
The offline scripts generate synthetic fixtures only, use no secrets or network, and test 305 archive records and a single-job USD cash movement contract. Local result: 7 archive + 5 commercial test cases passed. SQLite is not PostgreSQL or a permission test.

## Commercial model
Use immutable canonical job identity (source base, table, job record ID); one job to many verified movements. Keep quote, invoice, accepted scope, deposit request and actual receipt distinct. A payment receipt has stable accounting-system + external movement ID, linked job, USD integer cents, settled date, type, settlement status, evidence reference and recorded/verified provenance. Replays of the same event must be no-ops; conflicting contents must fail and require human review. Refunds are distinct actual movements linked to original receipt in future ledger; no implicit reversal. Phase 1 synthetic function only handles single-job settled receipts, refunds, operator payouts, materials and fees. Reject nonsettled, unknown type, wrong job or currency, invalid amount and missing evidence. Multiple-job allocations, refund caps, currency conversion, global unique movement IDs across jobs, cross-provider deduplication, actual evidence validation and database persistence are out of scope; required before integration. An invoice is not cash. Deposits and final receipts are distinct payments, not duplicated invoice totals. Cash after direct payments is not accounting profit or earned revenue; track gross project value, earned DCC revenue, pass-throughs, accrued direct costs, founder labor/time, processing fees and collection separately. QuickBooks remains accounting source, not this rehearsal. Do not count unaccepted quotes, forecasts, pass-through amounts or job components as validated paid projects.

2. Local PostgreSQL acceptance with synthetic fixture only, tested role grants, transaction atomicity, batch integrity and restore. Pin runtime versions; no hosted secrets.
3. Confirm backup/restore and retention authority; approved restricted export of actual Wave 1 records with independent counts and checksum, encrypted at rest, no payloads in GitHub/chat. Dry-run source readback and verify full ID set.
4. Separate explicit approval for hosted archive import. Verify destination isolation, permissions, manifest, all records and restore in disposable environment; no source deletion.
5. Separate approval to remove Airtable originals only after tested restoration, dependency signoff, reconciliation of changes, and rollback plan. Deletion may change Airtable record IDs on restoration; verify mapping and links, not just text. Capacity relief occurs only after removal.
6. Atlas evidence and observations are Wave 2, with reciprocal links and source review caveats; separately migrate and validate links. No public or operator consent inferred from historical research.
7. Commercial integration only after source-of-truth and ledger contract approval; first real paid project remains manual, never invent payment or assign an unconsenting operator.

No hosted migrations, data transfers, Airtable deletes, main merge, production activation, paid provisioning or outbound communication in Phase 1. Preserve Passport release branch; independent branch from main. Full CI and protected preview are separate release gates. Do not run optional live-key evaluation for this synthetic workstream.
